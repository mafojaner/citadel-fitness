Making the tiers sellable — after launch

Phases, not dates. Everything above this line has a day against it because the work and its order were both known. Past launch neither is: the sequence below is forced by dependency rather than calendar, and putting October dates on it would be inventing precision the plan doesn't have. Each phase starts when the one before it finishes.
Phase 1 — Billing, which gates everything else. Nothing can be sold until this exists, so no tier work matters before it. RevenueCat (one integration covering Play Billing and StoreKit), the products configured in each console, a subscriptions table carrying status/provider/period rather than today's single membership_tier column, an Edge Function verifying the provider's webhook signature and writing entitlement server-side, then the purchase and restore-purchases flows. Two weeks of real work, and the largest security surface the app will ever add — which is exactly why it sits after a launch gated on being confident the app is secure, not before it.
Blocks all
Phase 2 — Fortress goes on sale. It can, the moment billing works: nine features are already built, live in production and demonstrable. Nothing else is needed. Entitlement flips from the hand-granted column to whatever the webhook writes, and migration_036's column allowlist already prevents a client touching it.
Ready
Phase 3 — Valhalla cannot go on sale yet, and not for a code reason. All seven of its features are unbuilt, and four of them (form check, nutrition coaching, priority support, and the guides written monthly) need a person, not a deploy. Selling it before a coach exists would be taking money for nothing. The gate is: decide who delivers the human work, set a hard cap on reviews per member per month, and close enrollment when that cap is reached — a waitlist here is the feature, not the failure. At fifteen minutes a review and four a month, ten members is an evening a week and fifty is a job.
Blocked on people
Phase 4 — build what Valhalla actually sells. Ordered by what unblocks the tier soonest. Form check needs a submissions table, video upload and a review queue — the only one where the app itself is the bottleneck rather than the coach. Priority support is mostly routing: flag a member's feedback and answer it first. Nutrition coaching needs an intake form and somewhere for a coach to reply. Expert guides reuses the articles infrastructure already shipped, so it is writing rather than engineering.
After 3
Phase 5 — the four genuinely hard ones, on their own merits. AI progressive overload can start as a readable heuristic over logged history rather than a model, which is cheaper and easier to defend to a user. Wearable sync means HealthKit and Whoop, native permissions and a fresh Data Safety declaration. Offline sync is a local write queue plus conflict resolution — the hardest thing on this list, and the one most likely to lose data if rushed. Video demonstrations is filming 125 exercises: a production budget, not a sprint. None of these should be promised a date until the one before it is done.
Unscheduled
Standing rule — the catalogue is the contract. featureCatalog.ts drives every feature card, the tier grid and the comparison table, so a feature's tier and its wording move together or the pitch outruns the product. Three descriptions have already been corrected this way (tempo, challenges, and nutrition's “automatically”), and tests now pin the tier split, the no-automation promise, and that no shipped feature drifts out of Fortress.
Standing

Fortress: scope to operational

The gate is not real yet. membership_tier exists on profiles as a column with a check constraint, and that is the whole of it — no RLS policy on any table references it. Every Fortress feature is gated by useMembershipTier() in the client, which is a display rule. The Supabase anon key ships inside the app, so a free account can call PostgREST directly and read exactly what a member reads. This is the difference between selling a product and selling a hidden button, and it sits underneath all nine built features at once.
Seven-point bar for “done”. Reachable where you would look for it; reads real rows, not fixtures; gated server-side; scheduled infrastructure has actually fired; empty and failure states written; tested at the logic layer; and verified against a real account by a person. Nine features have working code. None has been verified by a person, and none is gated server-side — those two criteria are the bulk of the remaining work. Full detail in docs/fortress-scope.md.
Phase 1 applied to production 2026-08-20, and verified on both sides. Evidence, not assertion — the tables were empty, so rows were seeded for a free account and a member inside a transaction that then rolled back, and each account was impersonated at the database layer with its own JWT claims. Free account: saw 0 of 4 rows that exist and belong to it (goals, enrolment, group, membership); create_group refused; join_group_by_code refused; an rpe of 8.5 stored as NULL while the set itself still saved. Member: saw all 4, created a group, kept rpe 8.5. Structural checks: tier_rank is security definer with search_path="", owner reads rank 2, an unknown uuid reads 0, six policies reference it, the trigger is installed and both definer group doors carry the check. Nothing was written by any probe.
Phase 2: eight of the nine walked against real data, 2026-08-25. Advanced analytics, goal forecasting, PR vault (Bench Press 60 kg×8, 76 kg est. 1RM, served by the gated RPC) and private groups all open and render. Data export offers from the records screen. Structured programs list from the database, and a rollback probe confirmed the round trip: a member enrols, reads it back through RLS and the next session resolves to “Push”, while a free account is refused. RPE & rest timer render in the logging flow (Set / Weight / Reps / RPE, with the timer beneath). Refer & earn issues a real code and states plainly that the reward waits on billing. Weekly digest has its opt-in switch, but the send itself is Phase 3 and still unproven. Ninth is offline sync, which is unbuilt. Found and fixed along the way: all eight notification switches had no accessible name, so a screen reader announced them as “switch, on” with no idea what they controlled — React Native does not associate an adjacent label the way HTML does.
Phase 1 — make the gate real. A security definer helper returning the caller's tier rank (definer so the policy can read profiles without recursing through its own RLS — the trap that already bit group_members), then an RLS policy requiring that rank on every table behind a paid feature: records, goals, programs, groups, and the RPE columns on sets. The same check inside Edge Functions, which run with the service key and bypass RLS entirely. Each table gets an abort-probe run against production proving a free account gets zero rows. Two things already help: tier is one ordered column rather than scattered booleans, and migration_036's column allowlist already stops a member promoting themselves.
Applied & verified
Phase 2 — verify the nine. Walk each feature against real history with two accounts, one paid and one free, to check both sides of every gate: does the number agree with what the app shows elsewhere, does the empty state appear for a lift never performed, does the error state appear with the network off. The cheapest phase and the one skipped every time so far — hours of work that could surface days of it. It has to come after Phase 1, because verification done before the policies land would have to be redone after them.
8 of 9 verified
Phase 3 — prove the weekly digest fires. It is real code on a real schedule: .github/workflows/weekly-digest.yml, Sundays 17:00 UTC, calling the send-weekly-digest Edge Function through Resend. Scheduled in Actions rather than pg_cron on purpose, so no secret has to live inside a scheduled SQL statement. But no run has ever been observed and it depends on SUPABASE_FUNCTIONS_URL and WEBHOOK_SECRET being set. Trigger it by hand, watch the run, confirm the email lands with correct numbers and that opting out suppresses it — then let the schedule fire on its own for one week and check that it did.
Unproven
Phase 4 — offline sync, the only Fortress feature left that is real engineering. A local write queue, a reconnect reconciler, and a conflict rule. save_workout already does a full-day REPLACE, so last-write-wins per day falls out naturally — but that means a day edited on two devices silently loses one, which has to be a stated behaviour rather than a surprise. One to two weeks, touching every write path. Last among the engineering because it is the only one that can slip without holding anything else up.
1–2 weeks
Phase 5 — decide on video demonstrations. Filming 125 exercises and hosting them is a production budget, not a sprint, and it is the one Fortress item no amount of engineering finishes. Recommendation: cut it from the tier until footage exists rather than ship it as a permanent teaser. A paid tier advertising something that never arrives is the fastest way to earn refunds.
Not code
Half-shipped, and honest about it. Refer & earn tracks attribution today and stores a reward_status; self-referral, duplicates and bogus codes are all blocked and probed. The reward itself cannot exist before billing does, and the catalogue copy already says so rather than promising it. Private groups enforces group membership at the row level and was probed, but not tier — a free account inside a group can still read it, which Phase 1 closes.
Standing
