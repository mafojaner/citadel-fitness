Still open — everything not finished, in one place

Compiled 2026-08-26 against the repo and the live project, not from memory. The plans below each track their own slice of work, so anything blocked in two places was easy to lose between them. This is the single list. It was twenty items when compiled.

Fully closed on 27 August: the privacy policy's content, the target-SDK and permissions review, and the Aug 14 performance pass. Reduced but not closed: the dependency audit (its one runtime finding is patched; seven build-time advisories remain), the screen-reader pass (roles done in code, listening on a device still open), and Valhalla's feature backlog (three of seven now built). Not on the list at all, because nobody knew about them: the save_workout outage and the weekly digest silently skipping every paying subscriber.

That leaves fourteen open — nine of which only the account owner can do, plus the six days of store work they have already cost. One item — the store enrollments — is on its own responsible for the entire Aug 21–31 column never starting. The engineering half is short by comparison, which is the honest shape of the project right now: it is not waiting on code.

3 September: Google Play has approved the account. The item that held the whole last third of August is half gone, and it is the half that can ship on its own — Android does not wait for Apple. What that unblocks is a real chain: a production build, an internal-testing track, testers with something to install, and the Play Data Safety form, whose answers were already written line by line on 27 August in docs/store-listing.md. What it does not unblock is billing, which waits on a RevenueCat account rather than on a store.

Approval also changed what is dangerous. The Play service account key is a credential that only exists after approval, and this repository is public — .gitignore covered Apple's .p8, .p12 and .jks and none of Google's. Fixed the same day, and checked with git check-ignore rather than by reading the file: four plausible names for that key would every one of them have been committed.
What is genuinely finished, so the list below is not read as the whole project. All ten Fortress features, nine of them walked against real data; four of Valhalla's eight (progressive overload, priority support's app half, form check, nutrition coaching); the server-side tier gate applied and probed on both sides; offline sync; the account centre, plans page and desktop rail rebuilt; the pricing flow; the privacy policy correct and served from citadelfitness.app; and billing's database half — subscriptions, subscription_rank, my_tier() — applied to production. 371 tests over 31 suites, lint and typecheck green, and the suite can now render components rather than only checking arithmetic. expo-doctor passes 21 of 21 as of 3 September.

Sentry source maps — the config half is done (3 September). The token is yours. @sentry/react-native was a bare string plugin in app.json with no organization or project, and the plugin said so on every build: “Missing config for organization, project. Environment variables will be used as a fallback” — with neither variable set. Without them a production build uploads no source maps, so the first crash from a real phone arrives as minified frames through index-9cb4215f….js, with no file or line in your own code. Crash reporting that appears to work and tells you nothing. It had never mattered because there had never been a production build.

The slugs did not have to be guessed: admin-sentry-health already carried them as DEFAULT_SENTRY_ORG and DEFAULT_SENTRY_PROJECT, so the plugin now names reitumetse-mafojane / citadel-fitness explicitly. Confirmed by running the same config evaluation before and after: the warning appears once, then zero times.

The DSN reads ingest.de.sentry.io, which suggests an EU-region org and a url override. It does not need one. An unauthenticated probe distinguishes the two: on sentry.io a nonsense org returns 404 and this org returns 401, so it resolves there; de.sentry.io returns 401 for everything and proves nothing. The plugin's default https://sentry.io/ is right, and matches what the health function already uses. Setting de.sentry.io on the strength of the DSN would have broken the upload while looking like diligence.

What is left is one credential. SENTRY_AUTH_TOKEN, as an EAS secret — deliberately not in app.json, which the plugin itself warns about and strips, since anything in that file ships inside the application package. Without it the build still succeeds and still uploads nothing, which is the failure worth knowing about in advance.

Branch protection on main. CI blocks on typecheck, lint, tests and the control-character scan, and a pre-push hook now runs the same four locally — but the hook is opt-in per clone and skippable with --no-verify, and CI itself runs after the push, so a red build lands on main before anyone sees it. A protection rule is the only version of this that cannot be forgotten. It needs repository settings, which is yours: Settings → Branches → Add rule for main, require a pull request, and require status checks to pass.

The status check is named verify, not CI. That is the job id in ci.yml; CI is the workflow name and selecting it matches nothing. A required check that matches nothing passes vacuously, which would leave the rule looking enabled while gating nothing — the same shape as every other silent guard this project has been caught by. Verify after enabling by pushing a deliberately broken branch and confirming the merge is actually blocked.

The repository is public, so this is available on the free plan.

Engineering still to do

The purchase flow — written 2 September, behind one flag. This row said “no buy button, no restore-purchases, no cancellation path”. All three now exist. src/lib/billing.ts holds the product ids, a billingAvailability() that returns a reason rather than a boolean, and purchase() / restore() with the SDK call marked and guarded. planAction gained buy and manage; the plans page renders a purchase button, a Restore purchases button Apple requires, and a Manage subscription deep link out to the platform's own settings — a link rather than an in-app cancel, because both stores own cancellation and a button that appears to cancel and does not is worse than none.

What is genuinely left is one line and two call sites. const SDK_INSTALLED = false. It is a constant rather than a try/require so the honest state of the feature is readable without running it, and so a failed require is a disabled button rather than a crash on the plans page.

The product ids are now enforced across the boundary rather than trusted. A test parses PRODUCT_TIERS out of the webhook source and checks both directions — nothing sellable the webhook cannot grant, nothing in the webhook the app cannot sell, and each id mapped to the tier actually sold. It also asserts the regex matched something, because a regex that matches nothing would let every other assertion pass against an empty object. The failure being guarded against is the worst one available here: a rename takes someone's money and grants them nothing, silently, and the first report is a person saying they paid and have no features.

Installing react-native-purchases is deliberately still not done. It is a native module and there is no expo-dev-client, so it removes the way the app runs on a phone today. Play approval means a dev build is now possible, which it was not on 26 August — but the RevenueCat account still does not exist, so installing early would cost the current workflow and buy nothing. It goes in with the first dev build.

Dependency audit — the one runtime finding is fixed (27 August). The previous entry here said these were “all in the build-tooling chain, no runtime path in the shipped bundle”. That was wrong. nanoid reaches the app through @react-navigation/native, which uses it for route keys at runtime, so it shipped in every bundle. The advisory needs a custom generator called with size zero and React Navigation calls nanoid() bare, so exposure was low — but “the vulnerable path is unreachable” and “it isn't in the bundle” are different claims and only one was true. Bumped to 3.3.18 in the lockfile; React Navigation's range already allowed it. Verified by exporting the web bundle, not just by re-running audit.

Seven high advisories remain and this time it is traced rather than assumed: every one reaches the tree only through eslint, jest, or the Metro bundler inside expo/react-native. They want the planned SDK bump, which is its own work.

Re-audited 3 September, after the SDK alignment: the seven are gone. Zero high, zero critical, twenty-two moderate, and those twenty-two trace to three roots rather than twenty-two problems. @xmldom/xmldom arrives through config-plugins and prebuild-config; uuid through xcode, an iOS project tool. Both build-time.

The third was traced rather than filed, because this row has been wrong in exactly that way before. decode-uri-component reaches the app through query-string through @react-navigation/core, so it ships in the bundle. The vulnerable decode is only entered through React Navigation's getStateFromPath, which runs only when a linking config is passed to NavigationContainer — and neither container passes one. The app's own deep-link handling, parseRecoveryTokensFromUrl, uses the platform URLSearchParams instead. Present, and not on a reachable path: the two claims that got conflated over nanoid in August, checked separately this time.

It is conditional, which is worth writing down. Adding deep-link routing later — a linking config, so a notification can open a screen — activates this advisory, and there is no upstream fix available. That is a thing to re-check at the time, not to assume.

Standing hazard — inserting an article emails everyone

on_article_created fires notify_newsletter_email() on every INSERT into public.articles. It calls net.http_post to the send-newsletter-email function, so any row added to that table sends a real newsletter to every opted-in user.

This is worth a heading because the last migration to touch that table checked for it and found nothing. 20260101000026 says in its own comments: “no Database Webhook is currently live on public.articles (queried pg_trigger directly — zero rows), so these seed rows will NOT trigger any real email”. That was true then. The trigger was wired in 20260101000028 and it is live now, so the check has to be repeated rather than inherited.

The near miss: the first draft of 20260827150000 self-tested by inserting a test article and deleting it in the same transaction. The delete would have removed the article and still committed the pg_net queue row — a “SELF TEST GUIDE” newsletter to every subscriber, with nothing left in the table to explain it. The migration now writes nothing and asserts the policy's shape; the behavioural test runs as a rolled-back probe, where the queue row rolls back too. That probe reports it queued 2 rows, which is how we know this is real and not a theory.

Incident — logging was broken for six days

Every workout save failed, on every tier, from 20 to 27 August. 20260820020000 added rpe to save_workout's set_entries insert: the column went into the target list, no expression went into the VALUES list. Nine targets, eight expressions, with rpe's expression sitting in distance_unit's slot. Postgres refuses the statement with 42601, which aborts the function and fails the save. Nothing was written, so no data was lost or corrupted — saves people believed had worked simply never landed, and anything from those six days needs re-entering.

Three gates were green over it. db push reported success, because Postgres does not validate an INSERT's shape against its table at CREATE FUNCTION time. The suite is all pure functions and cannot see inside a .sql file. And the 25 August walk recorded RPE as verified — but what was checked was that the input renders in the logging flow, not that a save carrying one succeeds. A field can render perfectly and still be unsaveable, and that distinction is the whole lesson.

Fixed and confirmed against production before and after by calling the deployed function as a free account in a transaction that rolled back. The migration now ends by running itself for real and checking the row. A jest guard counts insert columns against values across every migration, and a smoke test since run against all eleven client-called RPCs found no other broken one.

Security sprint — three of four checks done, the fourth is yours (1 September).

1. backfill-welcome-emails auth: confirmed, and not by reading the file. The function carries a comment claiming it is deployed with JWT verification on. The deployment itself reports verify_jwt: true, which is the claim that actually matters. It was deliberately not probed over HTTP: that function ignores its request body entirely, so an unauthenticated call to test whether the gate is open would be the backfill, mailing every user still missing a welcome email.

2. The three functions deployed with JWT verification off. The same listing turned these up — send-welcome-email, send-newsletter-email and send-weekly-digest are open by design, because a webhook and a cron job have no JWT to present. Each checks an x-webhook-secret header as its first statement and fails closed, including when the secret is unset (a missing header is null, an unset secret is undefined, and the comparison rejects either way). WEBHOOK_SECRET is in fact set on the project, so the check has something real to compare against. The deployed source of all four was downloaded and diffed against the repo — byte-identical, so the guard on the page is the guard that is running.

3. The app path: 42501, exactly as this row predicted. Run against production under an impersonated authenticated role — the same request.jwt.claims and set role PostgREST performs per request — inside a transaction ending in raise exception, so nothing was committed. update profiles set fortress_since returned 42501 permission denied. The probe also wrote to name in the same session and that succeeded, which is the part that makes the result mean anything: without the control, a denial could equally have been the impersonation never taking effect. The value was written back to its own current value, so even the failing case would have changed nothing. What this does not cover: the HTTP hop. It proves the grant and policy refuse the write, which is where the refusal originates, but no browser session was driven through the REST API to watch the 403 arrive.

4. Rotate long-lived secrets — still open, and only you can do it. Two are worth rotating and nine are not: RESEND_API_KEY (set 5 Aug, 27 days old, can send mail as the domain) and WEBHOOK_SECRET (set 8 Aug, and the only thing standing in front of the three open endpoints above). The rest are either not secrets at all (ADMIN_EMAIL, EMAIL_FROM) or platform-managed and auto-injected. The plan's finding was that integration was by far the weakest of the three axes and the cheapest to fix — almost none of it needed new data, only for the app to use what it was already computing.

1. Fortress reaches the launch screen. Home carried exactly one paid card and it was a Valhalla teaser for nutrition coaching, which is not built — so the screen that opens on launch advertised the one thing that does not exist and none of the ten that do. Unproven
Phase 4 — offline sync. Built. Workout saves that cannot reach the server are queued, persisted and retried; the decisions live in lib/offlineQueue.ts as pure functions with fifteen tests, because this is the code that decides whether someone's data survives. Conflict resolution falls out of the server rather than being invented: save_workout replaces a day wholesale, so of two queued saves for one date only the later can win, and the queue collapses them by date. p_logged_same_day is captured when the person hits save rather than recomputed at flush, so a workout logged tonight and synced tomorrow keeps the reward eligibility it earned. Only failures that never reached the server are retried — a permission denial fails identically forever, and retrying it would hide a real bug behind an indicator that never clears. No connectivity library on purpose: a reachability flag lies on captive portals, so attempting the request is the only honest test. Free accounts are not queued but lose nothing either, since the draft store is persisted and they retry by hand.
